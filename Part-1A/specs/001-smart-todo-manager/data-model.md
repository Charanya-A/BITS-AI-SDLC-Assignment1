# Data Model: Smart Todo & Task Manager

## Domain Overview

The application manages a single user’s task collection stored as a JSON file in the backend. The API exposes operations on a canonical `Task` resource, and the frontend displays the task list, status, filters, and sorting output without mutating the persisted collection directly.

## Entity: Task

| Field | Type | Required | Rules |
|---|---|---:|---|
| id | string | Yes | Stable unique identifier; UUID v4 format |
| title | string | Yes | Trimmed, 1-120 characters |
| description | string | Yes | Required field, may be empty, max 2000 characters |
| priority | string | Yes | Enum: `LOW`, `MEDIUM`, `HIGH` |
| tags | string[] | No | Defaults to empty array; each item trimmed and non-empty |
| status | string | Yes | Enum: `PENDING`, `IN_PROGRESS`, `COMPLETED`; defaults to `PENDING` on create |
| createdAt | string | Yes | Server-generated UTC ISO 8601 timestamp |
| updatedAt | string | Yes | Server-generated UTC ISO 8601 timestamp |

### Example

```json
{
  "id": "3f5d1f3e-4d12-4a2d-9e08-f0ad0d5c1b2a",
  "title": "Prepare assignment draft",
  "description": "Outline sections and gather references.",
  "priority": "HIGH",
  "tags": ["college", "writing"],
  "status": "IN_PROGRESS",
  "createdAt": "2026-11-05T12:00:00.000Z",
  "updatedAt": "2026-11-05T12:10:00.000Z"
}
```

## Task Collection

The persistence layer stores a JSON array at the task-store path. The backend loads the array into memory, validates each item, and then exposes the collection through the REST API.

Rules:
- The task store may be empty or missing and is initialized as an empty array.
- A malformed or unreadable existing JSON file must stop startup with a clear error and preserve the original file.
- Failed writes must use atomic replacement with a temporary file to avoid partial JSON writes.
- The task list order in the JSON file is not the primary sort rule; sorting is applied in the API response layer only.

## Validation Rules

- Title: required, trimmed, 1-120 chars.
- Description: required field, may be empty string, max 2000 chars.
- Priority: must be one of `LOW`, `MEDIUM`, `HIGH`.
- Tags: optional; if present, must be an array of trimmed non-empty strings. Unknown or empty values are rejected. When omitted on create, default is an empty array.
- Status: allowed values are `PENDING`, `IN_PROGRESS`, and `COMPLETED`; defaults to `PENDING` on creation.
- Server-generated fields: `id`, `createdAt`, and `updatedAt` are generated by the backend and must not be client-controlled.
- Ordinary `PATCH /api/tasks/:id` accepts only `title`, `description`, `priority`, and `tags`; `status` is rejected through this endpoint and must use the dedicated status endpoint.
- Empty PATCH request bodies, unknown fields, and client-supplied ID/time fields are rejected before persistence.
- Failed validation rejects the request before any persistence change is applied.

## State Machine

Task status values and transitions are strict:

- `PENDING -> IN_PROGRESS`
- `IN_PROGRESS -> COMPLETED`
- All other transitions, including repeated current-state requests, are rejected.

Examples of rejected transitions:
- `PENDING -> PENDING`
- `PENDING -> COMPLETED`
- `IN_PROGRESS -> IN_PROGRESS`
- `COMPLETED -> IN_PROGRESS`
- `COMPLETED -> PENDING`

## Relationships

- One task is independent of other tasks; updates or deletes must affect only the selected task.
- Tags are a list of strings on each task, not a separate collection entity.
- Filtering is performed by matching tag values case-insensitively.
- Priority sorting is computed from the task collection at read time and does not rewrite the persisted JSON file.
